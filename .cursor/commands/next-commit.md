# 次のコミット単位まで作業を進める

`docs/roadmap.md` の作業計画から、次にコミットすべき1単位の作業を実装する。コミットはしない。

## 手順

1. 前提を読む
   - `.cursor/rules/project.mdc`
   - `.cursor/rules/commit-message.mdc`
   - `docs/roadmap.md`

2. 作業ツリーの状態を確かめる
   - `git status` と `git diff --stat` を実行する。
   - 未コミットの変更があり、それが次の作業と別の目的なら、作業を始めずに利用者へ報告し、先にコミットするか確認する。
   - 未コミットの変更が次の作業の途中なら、その続きから進める。

3. 次の作業を決める
   - `docs/roadmap.md` で最初の未完了項目（`- [ ]`）を次の作業にする。
   - 利用者がこのコマンドに引数や補足を付けた場合は、それを優先する。
   - 1項目が大きすぎて1コミットに収まらないと判断したら、roadmap の項目を分割してから、最初の部分だけを実装する。

4. 実装する
   - その項目の「完了条件」を満たす範囲だけを変更する。次の項目の作業を先取りしない。
   - 寸法、価格、カットロスなどの数値は `src/design/` に集め、表示側に直書きしない。
   - 設計判断（部材の配置、寸法の決め方など）をしたときは、その理由を `docs/design-notes.md` に追記する。

5. 確認する
   - Docker Compose の環境ができている段階なら、次を実行し、すべて通るまで直す。
     - `docker compose run --rm format`
     - `docker compose run --rm lint`
     - `docker compose run --rm test`
   - まだ Docker Compose の環境がない段階なら、実行できる確認だけを行い、未確認の項目を報告に書く。
   - 画面に関わる変更は、可能ならブラウザで表示を確かめる。

6. roadmap を更新する
   - 完了した項目を `- [x]` にする。
   - 作業中に見つかった追加作業は、適切な位置に未完了項目として足す。

7. 報告する
   - 実装した内容、確認した内容と結果、確認できなかった内容を分けて書く。
   - 最後に、`/commit-message` でコミットメッセージを検討できることを伝える。

## 守ること

- `git commit`、`git push` は実行しない。
- 1回の実行で扱うのは roadmap の1項目だけにする。
