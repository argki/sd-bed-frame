# 未コミットの変更からコミットメッセージを検討する

作業ツリーの未コミットの変更を読み、`.cursor/rules/commit-message.mdc` に従ったコミットメッセージを提案する。コミットはしない。

## 手順

1. 規約を読む
   - `.cursor/rules/commit-message.mdc`

2. 変更を集める
   - `git status --short`
   - `git diff --staged`
   - `git diff`
   - 未追跡ファイルは中身を読む。
   - 直近の履歴を `git log --oneline -n 10` で確認し、scope の付け方を既存のコミットにそろえる。

3. 変更の目的を整理する
   - 変更を目的ごとに分類する。
   - `docs/roadmap.md` で今回完了にした項目があれば、その目的と照らし合わせる。
   - 目的が複数あるときは、1コミットにまとめず分割を提案する。分割案ごとに、含めるファイル（または hunk）と `git add` のコマンド例を示す。
   - ステージ済みの変更がある場合は、ステージ済みの分を1コミットとして扱い、未ステージの分は別に扱う。

4. メッセージを書く
   - コミットごとに、規約の形式でメッセージを1案書く。type の選び方に迷う場合は、もう1案を理由とともに示す。
   - 本文には、diff から読み取れる理由、または roadmap と `docs/design-notes.md` に書かれている理由だけを書く。理由が読み取れないときは本文を推測で作らず、利用者に理由を尋ねる。

5. 出力する
   - 各コミットについて、次の順で示す。
     - 含める変更の一覧
     - コミットメッセージ（コードブロック）
     - そのまま使えるコマンド例（`git commit -F - <<'EOF'` の形式）
   - 規約に照らして気になる点（変更が大きすぎる、無関係なファイルが混ざっているなど）があれば最後に書く。

## 守ること

- `git add`、`git commit` は利用者が指示したときだけ実行する。
